## <a id="content1">与测试人员登录账号不一致</a>

测试人员发现一个大方iOS的崩溃。但这个崩溃只在她那台机器复现，这台机器又不是测试机。      
所以只能通过xcode找到对应的设备，查看设备日志，大致定位。    

最后发现：    
不是设备的问题，是我登录的账号跟测试人员登录的账号不一样。       
测试人员的账号在当前业务没有数据返回而端上没有做空保护导致的崩溃。        

收获：    
复现问题时首先要核对环境是否一致：账号、设备、版本等等     


## <a id="content2">打包编译报错</a>

删除了podfile.lock文件，重新生成后提交到了远程git。     
重新生成的lock文件，个推依赖的GTCommonSDK 由3.1.10.0 在pod install时 自动拉取了 3.2.6.0的版本。        
这个版本是 Xcode16 编译，带 Swift C interop overlay 符号。但打包机是xcode15.2，Xcode15 SDK 不存在这几个库,所以一直报链接错误。        
（这也是为什么我本机编译不报错，而打包机编译报错的原因，因为xcode版本不同）。      

解决方法：
1、升级打包机的xcode到16    
2、指定pod 'GTCommonSDK','3.1.10.0'    

然后去查看了打包成功的大方的podfile.lock文件的GTCommonSDK的版本，使用的是3.1.10.0，所以在podfile内指定了GTCommonSDK版本解决了问题。     

收获：    
遇到编译问题，通过日志基本可以定位到大概方向。     
以前能编译过去，现在编译过不去了，跟以前做下对比，根据编译日志，想想可能性。   
<span style="color:red;">注意非显性依赖的三方库的版本，删掉podfile.lock重新生成后有可能发生改变。</span>
